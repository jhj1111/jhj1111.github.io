# Part 1. 도메인 인터페이스 명세

## 1.1 목적

- OCR/번역 기능을 "무엇을 하는가(계약)"와 "어떻게 하는가(구현)"로 분리
- ML Kit ↔ 외부 AI 모델(Gemma 등) 교체 시 이 문서에 정의된 계약만 지키면 상위 레이어 수정 없이 동작해야 함

## 1.2 도메인 모델

```kotlin
data class DocumentImage(
    val bitmap: Bitmap,
    val sourceType: SourceType,   // CAMERA, GALLERY, PDF_PAGE
    val pageIndex: Int? = null,   // PDF인 경우 페이지 번호
)

enum class SourceType { CAMERA, GALLERY, PDF_PAGE }

data class RecognizedText(
    val fullText: String,
    val blocks: List<TextBlock> = emptyList(),  // 좌표 필요 없는 어댑터는 빈 리스트 허용
)

data class TextBlock(
    val text: String,
    val boundingBox: RectF?,   // 좌표 정보 없는 모델(LLM 등)은 null 허용
)

enum class LanguageCode(val bcp47: String) {
    KOREAN("ko"), ENGLISH("en"), JAPANESE("ja"), CHINESE("zh"),
    AUTO_DETECT("auto")
}
```

- `boundingBox`를 nullable로 설계해 좌표를 제공하지 않는 LLM 기반 어댑터도 동일 모델로 수용
- `TextBlock` 리스트가 비어도 `fullText`만으로 상위 로직이 동작 가능해야 함 (필수 아님)

## 1.3 TextRecognizer 인터페이스

```kotlin
interface TextRecognizer {
    /** 모델/리소스 준비. SDK 계열은 즉시 반환 가능, LLM 계열은 파일 로딩 등 시간 소요 가능 */
    suspend fun prepare()

    /** 준비 완료 여부 확인 */
    suspend fun isReady(): Boolean

    /** 이미지에서 텍스트 인식 수행 */
    suspend fun recognize(input: DocumentImage): Result<RecognizedText>

    /** 리소스 해제 (메모리 반환) */
    fun release()
}
```

### 계약 조건 (Contract)
- `recognize()` 호출 전 `isReady()`가 false면 내부적으로 `prepare()`를 자동 호출하거나, 호출자가 명시적으로 `prepare()`를 먼저 호출해야 함 (구현체별로 정책 통일 필요 — 권장: 자동 호출)
- 실패 시 예외를 던지지 않고 `Result.failure(DomainError로 매핑된 예외)` 반환
- `recognize()`는 취소(coroutine cancellation) 가능해야 함 (긴 추론 중 화면 이탈 시 안전 취소)
- 동일 입력에 대해 여러 번 호출해도 내부 상태가 오염되지 않아야 함 (idempotent)

## 1.4 Translator 인터페이스

```kotlin
interface Translator {
    suspend fun prepare()
    suspend fun isReady(): Boolean

    suspend fun translate(
        text: String,
        sourceLang: LanguageCode,
        targetLang: LanguageCode,
    ): Result<String>

    /** 지원 언어 목록 (동적 다운로드형 모델 대응) */
    suspend fun supportedLanguages(): List<LanguageCode>

    fun release()
}
```

### 계약 조건
- `sourceLang`이 `AUTO_DETECT`인 경우 내부적으로 언어 감지 후 번역 (지원하지 않는 어댑터는 `UnsupportedLanguage` 에러 반환)
- 긴 텍스트(문서 전체) 입력 시 내부적으로 청크 분할 처리 여부는 구현체 책임 (LLM 계열은 컨텍스트 길이 제한 고려)
- 번역 결과는 원문 서식(줄바꿈 등)을 최대한 보존

## 1.5 Summarizer 인터페이스

전체 문서 처리는 번역이 아닌 요약으로 제공한다 (온디바이스 모델의 컨텍스트/추론 시간 제약상, 요약이 출력 길이를 일정 수준으로 제어할 수 있어 더 적합). ML Kit에는 대응 API가 없어 외부 LLM 어댑터(Gemma 3n 등)로만 구현 가능하다.

```kotlin
interface Summarizer {
    suspend fun prepare()
    suspend fun isReady(): Boolean

    /** 문서 전체 텍스트를 요약한다. 컨텍스트 한계를 넘는 긴 문서는 구현체가 내부적으로 청크 분할 후 계층적 요약을 수행할 책임을 진다. */
    suspend fun summarize(text: String): Result<String>

    fun release()
}
```

### 계약 조건
- 입력 텍스트가 모델 컨텍스트 한계를 넘는 경우, 페이지/청크 단위로 나눠 개별 요약한 뒤 재요약하는 방식(hierarchical summarization)은 구현체 책임으로 둔다 (MVP는 컨텍스트 내에 들어가는 문서까지만 지원)
- 실패 시 `Result.failure(DomainError)` 반환 (원칙은 `TextRecognizer`/`Translator`와 동일)
- MVP는 ML Kit 어댑터가 없으므로, Summarizer를 요구하는 화면/기능은 외부 모델 어댑터가 준비된 이후(Phase 4)에만 노출한다

## 1.6 Repository 계층 (UseCase가 사용하는 상위 추상화)

```kotlin
interface DocumentRepository {
    suspend fun extractPages(fileUri: Uri): Result<List<DocumentImage>>

    /**
     * 페이지별 텍스트를 반환한다. 내부적으로 PdfBox 텍스트 레이어 추출을 우선 시도하고,
     * 텍스트가 없는 페이지는 자동으로 OCR로 폴백한다. 호출자는 어떤 경로로 추출됐는지 알 필요가 없다.
     */
    suspend fun extractPageText(fileUri: Uri, pageIndex: Int): Result<RecognizedText>
}
```

- `RecognizedText`를 반환 타입으로 통일해, 카메라 OCR 결과와 PDF 추출 결과를 동일한 번역/결과 UI 컴포넌트로 처리할 수 있게 한다
- `TextBlock.boundingBox`는 향후 PDF 좌표(TextPosition) 기반 레이아웃 보존 번역(원문 위치에 번역 겹쳐 보여주기)으로 확장할 것을 염두에 두고 nullable로 유지한다 (현재는 MVP 범위 밖)

## 1.6 UseCase 예시

```kotlin
class RecognizeAndTranslateUseCase(
    private val textRecognizer: TextRecognizer,
    private val translator: Translator,
) {
    suspend operator fun invoke(
        image: DocumentImage,
        targetLang: LanguageCode,
    ): Result<Pair<RecognizedText, String>> {
        val recognized = textRecognizer.recognize(image).getOrElse { return Result.failure(it) }
        val translated = translator.translate(
            recognized.fullText, LanguageCode.AUTO_DETECT, targetLang
        ).getOrElse { return Result.failure(it) }
        return Result.success(recognized to translated)
    }
}
```

```kotlin
class SummarizeDocumentUseCase(
    private val summarizer: Summarizer,
) {
    suspend operator fun invoke(pages: List<RecognizedText>): Result<String> {
        val fullText = pages.joinToString("\n\n") { it.fullText }
        return summarizer.summarize(fullText)
        // TODO(Phase 4 이후): fullText가 컨텍스트 한계를 넘는 경우 청크 분할 + 계층적 요약 적용
    }
}
```

## 1.7 어댑터 구현 체크리스트 (신규 모델 추가 시)

- [ ] `TextRecognizer`, `Translator`, `Summarizer` 중 해당하는 인터페이스를 정확히 구현했는가
- [ ] 모든 실패 케이스를 `DomainError`로 매핑했는가 (원본 예외를 그대로 노출하지 않는가)
- [ ] `prepare()`/`isReady()`/`release()`를 실제 리소스 생명주기에 맞게 구현했는가
- [ ] coroutine 취소를 지원하는가 (`ensureActive()` 등 체크)
- [ ] 해당 어댑터의 DI 모듈을 등록했는가
- [ ] 평가셋 기준 정확도/속도 벤치마크를 기록했는가 (테스트 전략 문서 참조)

# Part 2. 테스트 전략 문서

## 2.1 테스트 레벨 구분

| 레벨 | 대상 | 도구 | 특징 |
|---|---|---|---|
| Unit Test | domain UseCase, Reducer, 유틸 함수 | JUnit5, MockK, Turbine | 순수 로직, 모델 mock 처리, 빠름 |
| ViewModel Test | State/Intent/Effect 흐름 | JUnit5, Turbine, kotlinx-coroutines-test | Mock UseCase 주입 |
| Adapter Integration Test | ML Kit/Gemma 어댑터 실제 동작 | Android Instrumented Test | 실기기/에뮬레이터 필요 |
| 모델 평가 (Evaluation) | OCR 정확도, 번역 품질 | 자체 스크립트 + 평가셋 | 결정론적이지 않으므로 unit test와 분리 |
| UI Test | 화면 흐름 | Compose UI Test / Espresso | 주요 시나리오 위주로 최소화 |
| Benchmark | 추론 속도, 메모리, 배터리 | Macrobenchmark, Android Profiler | Phase 5에서 본격화 |

## 2.2 Mock 전략

- domain/ViewModel 테스트는 `TextRecognizer`/`Translator`의 Fake 구현체를 사용
  ```kotlin
  class FakeTextRecognizer(
      private val result: Result<RecognizedText> = Result.success(RecognizedText("dummy")),
  ) : TextRecognizer {
      override suspend fun prepare() {}
      override suspend fun isReady() = true
      override suspend fun recognize(input: DocumentImage) = result
      override fun release() {}
  }
  ```
- Phase 2(전체 화면 흐름 구축) 단계에서 이 Fake 구현체를 실제 DI에 연결해 UX를 먼저 완성

## 2.3 모델 평가(Evaluation) 전략

모델 추론 결과는 비결정적이거나 품질 기준이 모호하므로 pass/fail unit test로 다루지 않고 별도 평가 파이프라인으로 관리한다.

- **평가셋 구성**: 카메라 촬영/스캔 문서/일반 인쇄물 등 카테고리별 이미지 30~50장 + 정답 텍스트(ground truth)
- **OCR 평가 지표**: CER(Character Error Rate) 또는 단순 Levenshtein 거리 기반 유사도
- **번역 평가 지표**: 정량 지표(BLEU 등)는 참고용, 정성 평가(사람이 직접 자연스러움 확인)를 우선
- **비교 리포트**: 어댑터별(ML Kit vs Gemma 등) 정확도/속도/메모리 사용량을 표로 정리해 문서화 (PRD의 성공 기준과 연결)

## 2.4 CI 통합

- Unit test + ViewModel test는 PR마다 자동 실행 (GitHub Actions 등)
- Instrumented test/Evaluation은 무거우므로 main 브랜치 병합 시 또는 수동 트리거로 실행
- 커버리지 리포트(Jacoco/Kover)는 domain 모듈 중심으로 측정, feature 모듈은 참고용

## 2.5 에러 케이스 테스트 우선순위

- [ ] 모델 로딩 실패 (파일 없음/손상)
- [ ] 추론 중 OOM 발생 시 앱 크래시 없이 에러 상태 전환
- [ ] 지원하지 않는 언어 조합 요청
- [ ] PDF 파싱 실패 (암호화된 PDF, 손상된 파일)
- [ ] 네트워크 없는 상태에서 모델 최초 다운로드 실패
- [ ] 추론 중 화면 이탈로 인한 coroutine 취소 정상 처리

## 2.6 벤치마크 항목 (Phase 5)

- 어댑터별 추론 지연시간(latency) — 이미지 1장 기준

- 앱 시작 시간(Cold Start)에 모델 로딩이 미치는 영향
- APK/설치 용량 (모델 번들 여부에 따른 비교)
