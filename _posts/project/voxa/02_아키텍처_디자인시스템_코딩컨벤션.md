# 아키텍처 설계 문서 / 디자인 시스템 문서 / 코딩 컨벤션 가이드

---

# Part 1. 아키텍처 설계 문서

## 1.1 설계 목표

- 재사용 및 유지보수 가능한 구조 우선, 보일러플레이트가 늘더라도 구조 원칙 유지
- SOLID 원칙 준수
- MVI 아키텍처 채택
- Hilt 기반 DI
- AI 모델(OCR/번역) 교체가 도메인·UI 레이어 수정 없이 가능한 구조

## 1.2 레이어 구조

```
presentation (UI, ViewModel, MVI State/Intent/Effect)
        ↓ 의존
domain (UseCase, Repository Interface, Model Interface, Domain Model)
        ↑ 구현
data / feature-adapter (Repository 구현체, ML Kit/Gemma 어댑터)
```

- **domain 계층은 Android 프레임워크에 의존하지 않는다.** (순수 Kotlin 모듈)
- presentation은 domain의 UseCase만 호출하고, 구체 구현(ML Kit 등)을 알지 못한다.
- data/adapter 계층이 domain에 정의된 인터페이스를 구현한다. (의존성 역전)

## 1.3 모듈 구조 (제안)

```
:app                        # 진입점, DI 그래프 조립, 네비게이션 호스트
:core:ui                    # 디자인 시스템 (컬러/타이포/스페이싱), 공통 Composable
:core:common                # 공통 유틸, 확장함수
:domain                     # UseCase, Repository/Model 인터페이스, 도메인 모델, 도메인 에러 타입
:data:document              # PDF/이미지 파일 처리 (텍스트 추출, 렌더링)
:feature:ocr-mlkit          # ML Kit OCR 어댑터 (TextRecognizer 구현체)
:feature:ocr-gemma          # Gemma 3n 기반 OCR 어댑터
:feature:translate-mlkit    # ML Kit Translate 어댑터
:feature:translate-gemma    # Gemma 3n 기반 번역 어댑터
:feature:camera             # 카메라 프리뷰/촬영 UI
:feature:result             # 인식/번역 결과 화면
```

- 모듈 의존 방향은 항상 `feature/data → domain → core:common` 이며, 역방향 금지
- `feature-*` 모듈끼리는 서로 의존하지 않는다. (필요 시 domain UseCase로 조합)
- 이 구조를 강제해야 "모델 교체 = 모듈 교체"가 실제로 컴파일 타임에 보장됨

## 1.4 도메인 인터페이스 (요약, 상세는 별도 문서 참조)

```kotlin
interface TextRecognizer {
    suspend fun recognize(input: DocumentImage): Result<RecognizedText>
    suspend fun isReady(): Boolean
    suspend fun prepare()  // 모델 로딩 (필요 시)
    fun release()
}

interface Translator {
    suspend fun translate(
        text: String,
        sourceLang: LanguageCode,
        targetLang: LanguageCode
    ): Result<String>
    suspend fun isReady(): Boolean
    suspend fun prepare()
    fun release()
}
```

- 반환 타입은 항상 `Result<T>` 또는 sealed class 기반 도메인 에러로 래핑 (예외 직접 노출 금지)
- `prepare()`/`isReady()`를 인터페이스 레벨에 포함해 LLM 계열의 느린 초기화를 처음부터 수용

## 1.5 MVI 구조

```kotlin
data class ScreenState(
    val isLoading: Boolean = false,
    val recognizedText: String? = null,
    val translatedText: String? = null,
    val error: DomainError? = null,
)

sealed interface ScreenIntent {
    data class CaptureImage(val image: DocumentImage) : ScreenIntent
    data class SelectFile(val uri: Uri) : ScreenIntent
    data class ChangeLanguage(val target: LanguageCode) : ScreenIntent
}

sealed interface ScreenEffect {
    data class ShowToast(val message: String) : ScreenEffect
    data object NavigateToResult : ScreenEffect
}
```

- State: 화면에 항상 보여지는 지속 상태, 불변(immutable) 유지
- Intent: 사용자 행동/이벤트 입력
- Effect: 일회성 이벤트(토스트, 네비게이션) — State와 분리, `Channel`/`SharedFlow`로 처리
- Reducer(State + Intent → State)는 순수 함수로 작성, ViewModel 내부 별도 함수로 분리하여 단위 테스트 용이하게 유지

## 1.6 에러 처리 전략

```kotlin
sealed interface DomainError {
    data object ModelNotReady : DomainError
    data object ModelLoadFailed : DomainError
    data object OutOfMemory : DomainError
    data object UnsupportedLanguage : DomainError
    data object FileParsingFailed : DomainError
    data class Unknown(val cause: Throwable) : DomainError
}
```

- 모든 어댑터(ML Kit/Gemma 등)는 내부 예외를 위 `DomainError`로 매핑해서 반환
- UI는 `DomainError` 타입에 따라 분기 처리 (재시도 버튼, 안내 문구 등)

## 1.7 DI (Hilt) 구성 원칙

- 모델 어댑터는 `@Binds`로 인터페이스-구현체를 연결, 모듈 단위로 관리
  ```kotlin
  @Module
  @InstallIn(SingletonComponent::class)
  abstract class OcrModule {
      @Binds
      abstract fun bindTextRecognizer(impl: MlKitTextRecognizer): TextRecognizer
  }
  ```
- 어댑터 교체 시 `@Binds` 대상만 변경 (혹은 flavor/설정 기반으로 런타임 선택 가능하도록 `@Named`/Qualifier 활용 고려)

## 1.8 테스트 아키텍처 개요

- domain UseCase → 순수 unit test (JUnit + MockK)
- ViewModel → State/Intent 기반 테스트 (Turbine 등으로 Flow 검증)
- 모델 어댑터 → 별도 evaluation 스크립트/벤치마크 (상세는 테스트 전략 문서 참조)

## 1.9 오픈 이슈 / 추가 검토 필요

- 런타임 모델 선택(설정 화면에서 ML Kit ↔ Gemma 전환) 지원 여부와 그에 따른 DI 전략 (Qualifier vs Factory 패턴)
- 대용량 모델 파일의 모듈 내 포함 여부 (assets vs 런타임 다운로드)
- Compose Multiplatform 등 향후 확장 가능성 고려 여부 (현재는 Android 단일 타겟 가정)

# Part 2. 디자인 시스템 문서

## 2.1 원칙

- 모든 시각 속성(컬러/스페이싱/타이포/모양)은 하드코딩 금지, 반드시 토큰을 통해 참조
- Light/Dark 모드는 semantic color naming으로 처리 (역할 기반 이름, 실제 값 아님)

## 2.2 컬러 토큰 (예시)

컬러는 2단계로 분리한다.

**디자인 컨셉: Soft Paper Minimal** — 차가운 AI/테크 인상을 지우고 따뜻한 종이 질감과 정갈한 스캐너 경험을 결합. 눈의 피로를 줄이는 Warm Cream 배경, 신뢰감을 주는 Sage Teal 포인트, 손에 감기는 완만한 곡선(Pill Shape)이 핵심.

1. **Raw 컬러 팔레트**: 실제 hex 값을 직관적인 이름(색상 계열 + 톤)으로 한 번만 정의
2. **Semantic 컬러 토큰**: 팔레트를 역할(primary, surface 등) 기준으로 매핑, 컴포넌트는 이 semantic 토큰만 참조

```kotlin
// core:ui - Raw 컬러 팔레트 (색상/톤 이름으로 직관적 확인 가능, hex는 여기서만 등장)
object ColorPalette {
    val WarmCream       = Color(0xFFFDFBF7)  // 전체 배경
    val ParchmentBeige  = Color(0xFFF7F1E4)  // surface (배경보다 한 톤 진함, 카드 구분용)
    val SageTeal        = Color(0xFF3F7768)  // primary
    val SageTealDark    = Color(0xFF4F9C87)  // primary (다크모드용, 더 밝게)
    val DeepTerracotta  = Color(0xFFD96847)  // accent/secondary
    val LightTerracotta = Color(0xFFF0997B)  // accent (다크모드용)
    val Charcoal        = Color(0xFF2B2D42)  // textPrimary (라이트)
    val IvoryWhite       = Color(0xFFEDEAE3)  // textPrimary (다크)
    val SoftGray        = Color(0xFF6B7690)  // textSecondary (라이트)
    val SoftGrayLight   = Color(0xFF9AA6BC)  // textSecondary (다크)
    val OutlineBeige    = Color(0xFFEDE6D8)  // outline (라이트)

    val DarkCocoa       = Color(0xFF1E1A15)  // background (다크)
    val DarkSurface     = Color(0xFF2A241C)  // surface (다크)
    val DarkOutline     = Color(0xFF3A342B)  // outline (다크)
    val OnPrimaryDark   = Color(0xFF14211D)  // onPrimary (다크, 밝은 primary 위 어두운 텍스트)

    val White = Color(0xFFFFFFFF)
    val Red600 = Color(0xFFB00020)  // error (라이트)
    val Red300 = Color(0xFFCF6679)  // error (다크)
}

// core:ui - Semantic 컬러 토큰 (역할 기반, 컴포넌트가 실제로 참조하는 대상)
data class AppColors(
    val primary: Color,
    val onPrimary: Color,
    val background: Color,
    val surface: Color,
    val onSurface: Color,
    val accent: Color,
    val error: Color,
    val onError: Color,
    val outline: Color,
    val textPrimary: Color,
    val textSecondary: Color,
)

val LightColors = AppColors(
    primary = ColorPalette.SageTeal,
    onPrimary = ColorPalette.White,
    background = ColorPalette.WarmCream,
    surface = ColorPalette.ParchmentBeige,
    onSurface = ColorPalette.Charcoal,
    accent = ColorPalette.DeepTerracotta,
    error = ColorPalette.Red600,
    onError = ColorPalette.White,
    outline = ColorPalette.OutlineBeige,
    textPrimary = ColorPalette.Charcoal,
    textSecondary = ColorPalette.SoftGray,
)

val DarkColors = AppColors(
    primary = ColorPalette.SageTealDark,
    onPrimary = ColorPalette.OnPrimaryDark,
    background = ColorPalette.DarkCocoa,
    surface = ColorPalette.DarkSurface,
    onSurface = ColorPalette.IvoryWhite,
    accent = ColorPalette.LightTerracotta,
    error = ColorPalette.Red300,
    onError = ColorPalette.OnPrimaryDark,
    outline = ColorPalette.DarkOutline,
    textPrimary = ColorPalette.IvoryWhite,
    textSecondary = ColorPalette.SoftGrayLight,
)
```

- 컴포넌트 코드에서는 `AppTheme.colors.primary` 형태로만 참조, `Color(0xFF...)` 직접 사용 금지
- `ColorPalette`의 raw 값은 `LightColors`/`DarkColors` 정의 내부에서만 참조하고, 화면/컴포넌트 코드가 `ColorPalette`를 직접 참조하는 것도 금지 (semantic 레이어를 우회하면 다크모드 대응이 깨짐)
- 신규 색상이 필요하면 먼저 `ColorPalette`에 이름 있는 톤을 추가한 뒤, `AppColors`에 역할을 부여하는 순서를 지킨다
- `surface`와 `background`는 색상 자체로 구분되도록 의도적으로 톤 차이를 둠 (그림자만으로는 실외 환경에서 경계가 흐려질 수 있어 색상 분리를 우선하고, ambient shadow는 보조 수단으로만 사용)

## 2.3 스페이싱 & Shape 토큰

```kotlin
object Spacing {
    val none = 0.dp
    val xs = 4.dp
    val sm = 8.dp
    val md = 16.dp
    val lg = 24.dp
    val xl = 32.dp
    val xxl = 48.dp
}

object Radius {
    val sm = 12.dp     // 소형 칩, 인풋 필드
    val md = 16.dp     // 카드 패널, 바텀시트 모서리
    val lg = 20.dp     // 메인 콘텐츠 컨테이너
    val pill = 28.dp   // 주요 버튼, 언어 선택 토글 (완전한 pill 형태는 999.dp)
    val full = 999.dp
}
```

- Elevation: 강한 Drop Shadow 금지. Warm Cream 배경과 어우러지는 연한 Ambient Shadow(2~4dp)만 보조적으로 사용, 레이어 구분의 주 수단은 `surface` 색상 분리

## 2.5 다크모드 대응 체크리스트

- [ ] 모든 색상이 semantic token을 통해서만 참조되는가
- [ ] 이미지/아이콘 중 다크모드에서 별도 에셋이 필요한 것이 있는가 (예: 로고)
- [ ] 카메라 프리뷰 오버레이 등 다크모드에서 시인성이 떨어지는 요소는 없는가
- [ ] 시스템 다크모드 변경 시 런타임 리컴포지션이 정상 동작하는가

## 2.6 해상도/폼팩터 대응

- WindowSizeClass 기반 Compact/Medium/Expanded 레이아웃 분기 (특히 카메라 화면, 결과 화면)
- 카메라 프리뷰 종횡비와 실제 촬영 이미지 비율 불일치 처리 정책 명시
- 최소 지원 해상도/밀도 명시 (예: mdpi 이상)

## 2.7 다국어 UI 텍스트 리소스 정책

- UI 텍스트는 `strings.xml` / `strings-ko.xml` 등으로 관리
- **번역 결과 텍스트(런타임 동적 데이터)는 리소스화 대상이 아님** — 도메인 모델로 별도 관리, strings.xml과 혼동 금지
- 복수형(plural) 처리 대상 문자열 목록 별도 관리
- 신규 문자열 추가 시 모든 지원 언어 리소스에 누락 없는지 CI에서 검증 (lint 규칙 고려)

# Part 3. 코딩 컨벤션 가이드

## 3.1 네이밍 규칙

- 패키지: `com.{org}.voxa.{layer}.{feature}` (예: `com.example.voxa.domain.ocr`)
- 인터페이스: 역할 명사형 (`TextRecognizer`, `Translator`), `I` 접두사 사용 금지
- 구현체: `{공급자}{역할}` (`MlKitTextRecognizer`, `GemmaTextRecognizer`)
- UseCase: `{동사}{대상}UseCase` (`RecognizeTextUseCase`, `TranslateTextUseCase`)
- Composable 함수: PascalCase, 명사형 (`ResultScreen`, `CameraPreview`)
- State/Intent/Effect: `{Feature}State`, `{Feature}Intent`, `{Feature}Effect`

## 3.2 패키지 구조 규칙

```
domain/
  model/          # 도메인 모델 (RecognizedText, DocumentImage 등)
  repository/     # Repository 인터페이스
  usecase/        # UseCase 클래스
  error/          # DomainError 정의

feature-ocr-mlkit/
  MlKitTextRecognizer.kt
  di/OcrModule.kt
  internal/       # 외부에 노출하지 않는 내부 구현
```

- `internal` 가시성을 적극 활용해 모듈 간 불필요한 노출 최소화 (캡슐화)

## 3.3 커밋 메시지 규칙

- Conventional Commits 형식 권장: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`
- 예: `feat(ocr-gemma): Gemma 3n 기반 TextRecognizer 어댑터 구현`
- 하나의 커밋은 하나의 논리적 단위로 유지 (Phase 내 세부 작업 단위 권장)

## 3.4 린트/포맷 설정

- ktlint 또는 detekt 도입, CI에서 강제
- 최대 함수 길이/복잡도 규칙 설정 (예: Cyclomatic Complexity 15 이하)
- import wildcard 금지, unused import 자동 제거

## 3.5 주석/문서화 규칙

- public 인터페이스(domain의 Repository/UseCase)는 KDoc 필수
- "왜 이렇게 했는지"가 비직관적인 경우에만 인라인 주석 (코드가 스스로 설명되도록 작성 우선)

## 3.6 버전 관리

- Gradle Version Catalog(`libs.versions.toml`)로 모든 의존성 버전 중앙 관리
- 신규 라이브러리 추가 시 반드시 카탈로그 등록 후 사용 (직접 버전 하드코딩 금지)

## 3.7 로깅 규칙

- 로그 레벨 구분: DEBUG(개발용 상세), INFO(주요 흐름), WARN(복구 가능한 이상), ERROR(실패)
- 모델 추론 시간, 입력 크기 등 성능 관련 로그는 태그를 통일 (`Tag: "ModelPerf"`)
- 릴리즈 빌드에서는 DEBUG 로그 비활성화 (ProGuard/R8 규칙 또는 빌드 변형 분기)
- 사용자 문서 내용 등 민감할 수 있는 데이터는 로그에 원문 그대로 남기지 않음 (길이/해시 등으로 대체)
