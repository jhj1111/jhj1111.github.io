# 단계별 기능 구현 계획

앞서 정의한 PRD/아키텍처/도메인 인터페이스 문서를 기준으로, 실제 작업 순서를 Phase별 세부 태스크와 완료 조건(Definition of Done)까지 포함해 정리한다. 각 Phase는 이전 Phase의 완료 조건을 충족해야 다음으로 넘어간다.

---

## Phase 0 — 기획/문서화

### 목표
구현에 들어가기 전, 스코프와 구조를 문서로 고정한다.

### 태스크
- [ ] PRD 작성 (완료 — `01_PRD.md`)
- [ ] 아키텍처/디자인 시스템/코딩 컨벤션 문서 작성 (완료 — `02_아키텍처_디자인시스템_코딩컨벤션.md`)
- [ ] 도메인 인터페이스 명세/테스트 전략 작성 (완료 — `03_도메인인터페이스_테스트전략.md`)
- [ ] AGENT.md 작성 (완료 — `04_AGENT.md`)
- [ ] 리포지토리 생성, 라이선스/README 초안 작성

### 완료 조건 (DoD)
- 4개 기준 문서가 리포지토리에 커밋되어 있다
- 모듈 구조/의존 방향이 아키텍처 문서에 확정되어 있다

---

## Phase 1 — 기본 구조 수립

### 목표
기능 없이도 빌드/실행되는 스켈레톤 앱을 완성한다. UI/아키텍처/DI가 이 단계에서 확정된다.

### 1-1. 프로젝트/모듈 셋업
- [ ] 멀티모듈 프로젝트 생성 (`:app`, `:core:ui`, `:core:common`, `:domain`, `:data:document`, `:feature:*`)
- [ ] Gradle Version Catalog(`libs.versions.toml`) 구성
- [ ] ktlint/detekt 설정 및 CI 연동 (GitHub Actions)
- [ ] Hilt 기본 설정 (`@HiltAndroidApp`, 빈 `SingletonComponent` 모듈)

### 1-2. 디자인 시스템 구축
- [ ] `ColorPalette` / `AppColors` (Light·Dark) 정의
- [ ] `Spacing`, `Radius`, `AppTypography` 토큰 정의
- [ ] `AppTheme` Composable 작성 (다크모드 시스템 연동)
- [ ] 다크모드 전환 확인용 샘플 화면(Storybook 성격의 임시 화면)으로 토큰 시각 검증

### 1-3. 다국어 리소스 기반 구축
- [ ] `strings.xml` / `strings-ko.xml` 기본 골격 작성 (앱 이름, 공통 버튼 텍스트 등)
- [ ] 문자열 리소스 누락 검증용 lint 규칙 확인

### 1-4. 네비게이션/화면 골격
- [ ] Navigation 그래프 정의 (Camera → Result, Gallery/PDF → Result 등 화면 흐름만 배치)
- [ ] 각 화면을 빈 Composable(placeholder)로 생성해 네비게이션 흐름 확인

### 1-5. MVI 골격
- [ ] 공통 `MviViewModel` 베이스 클래스/인터페이스 작성 (State/Intent/Effect 처리 공통 로직)
- [ ] 화면별 `State`/`Intent`/`Effect` 클래스 초안 작성 (필드는 비어있어도 됨)

### 완료 조건 (DoD)
- 앱이 실기기/에뮬레이터에서 실행되며 화면 간 네비게이션이 동작한다
- 다크모드 전환 시 모든 화면 토큰이 정상 반영된다 (하드코딩 색상 없음)
- Hilt 의존성 그래프가 에러 없이 컴파일된다
- CI에서 ktlint/build가 통과한다

## Phase 2 — 도메인 인터페이스 및 Mock 어댑터로 화면 흐름 완성

### 목표
실제 모델 없이 전체 UX 플로우(입력→인식→번역→결과)를 완성한다.

### 2-1. 도메인 계층 구현
- [ ] `domain` 모듈에 `DocumentImage`, `RecognizedText`, `TextBlock`, `LanguageCode`, `DomainError` 정의 (명세 문서 기준)
- [ ] `TextRecognizer`, `Translator`, `DocumentRepository` 인터페이스 정의
- [ ] `RecognizeAndTranslateUseCase` 등 핵심 UseCase 구현

### 2-2. Mock/Fake 어댑터 구현
- [ ] `FakeTextRecognizer`, `FakeTranslator` 구현 (테스트 전략 문서 기준)
- [ ] Fake 어댑터를 Hilt 테스트/디버그 빌드 변형에 연결

### 2-3. 입력 UI 구현
- [ ] CameraX 전체 화면 프리뷰 (고정 프레임 가이드 없음, 촬영 버튼/권한 요청 플로우 포함)
- [ ] 문서 가장자리 자동 감지 및 accent 컬러 실시간 아웃라인 표시 (`06_UI_화면설계명세.md` 3.1 참조)
- [ ] 갤러리 이미지 선택 (Photo Picker API)
- [ ] PDF 파일 선택 (Storage Access Framework)

### 2-4. 결과 UI 구현
- [ ] 로딩/에러/빈 상태를 포함한 결과 화면 (Mock 데이터 기준)
- [ ] 언어 선택 UI (source/target)
- [ ] 번역 결과 텍스트 복사/공유 기능

### 완료 조건 (DoD)
- 카메라/갤러리/PDF 입력 세 경로 모두 Mock 데이터로 결과 화면까지 도달한다
- 권한 거부, 파일 선택 취소 등 예외 흐름에서도 크래시 없이 처리된다
- 모든 화면이 디자인 시스템 토큰만 사용한다 (다크모드 확인 포함)

## Phase 3 — ML Kit 기반 기능 구현 (동작하는 MVP)

### 목표
Mock 어댑터를 ML Kit 어댑터로 교체해 실사용 가능한 MVP를 완성한다.

### 3-1. OCR 어댑터
- [ ] `:feature:ocr-mlkit` 모듈 생성, `MlKitTextRecognizer` 구현
- [ ] 한국어/영어/일본어/중국어 등 스크립트별 인식기 분기 처리
- [ ] `DomainError` 매핑 (인식 실패, 언어 미지원 등)

### 3-2. 번역 어댑터
- [ ] `:feature:translate-mlkit` 모듈 생성, `MlKitTranslator` 구현
- [ ] 언어 모델 동적 다운로드 UX (다운로드 진행률, 저장 공간 부족 처리)
- [ ] 자동 언어 감지 연동

### 3-3. PDF 처리
- [ ] `:data:document` 모듈에서 PdfBox-Android 기반 텍스트 레이어 추출 로직 구현 (페이지 단위, 우선 시도)
- [ ] 텍스트 레이어가 없거나 비어 있는 페이지는 `PdfRenderer`로 Bitmap 변환 후 기존 OCR 파이프라인으로 내부 자동 폴백 (사용자에게 선택 UI 노출하지 않음)
- [ ] 두 경로 모두 `RecognizedText` 동일 도메인 모델로 반환하도록 통일
- [ ] 페이지 처리 후 Bitmap 명시적 `recycle()` (AGENT.md gotcha 반영)
- [ ] PDF 화면은 몰입형 전체 화면 리더로 구현 (기본 상태: 콘텐츠만 표시, 탭 시 반투명 상/하단 바 노출 — 06_UI_화면설계명세.md 3.2 참조)
- [ ] 번역은 현재 페이지 단위로 한정 (전체 문서 일괄 번역은 Phase 4 이후 요약 기능으로 대체)

### 3-4. DI 연결 및 Fake 대체
- [ ] Fake 어댑터 바인딩을 ML Kit 어댑터로 교체
- [ ] 어댑터 교체 시 domain/presentation 코드 미변경 여부 직접 검증 (아키텍처 목표 검증 포인트)

### 완료 조건 (DoD)
- 카메라/갤러리/PDF 입력 → 실제 OCR → 실제 번역까지 오프라인으로 동작한다
- Fake→ML Kit 교체 과정에서 `feature-*` 모듈 외 코드 변경이 없었음을 커밋 diff로 확인한다
- 자체 평가셋(30~50장) 기준 1차 OCR/번역 정확도 리포트 작성

## Phase 4 — 외부 AI 모델 어댑터 확장

### 목표
Gemma 3n 등 외부 오픈소스 모델 어댑터를 추가하고 ML Kit과 비교한다.

### 4-1. 모델 준비
- [ ] Gemma 3n 모델 파일 확보 및 라이선스 조건 확인
- [ ] MediaPipe LLM Inference API 연동 방식 결정 (앱 번들 vs 런타임 다운로드)
- [ ] 모델 다운로드/버전 관리 로직 (WorkManager 기반)

### 4-2. 어댑터 구현
- [ ] `:feature:ocr-gemma`, `:feature:translate-gemma` 모듈 생성
- [ ] AGENT.md의 "신규 AI 모델 어댑터 추가 절차" 체크리스트 준수
- [ ] `prepare()`/`isReady()` 기반 느린 초기화 처리, 로딩 UI 반영

### 4-2b. 문서 요약 기능 (PDF 전체 처리)
- [ ] `:feature:summarize-gemma` 모듈 생성, `Summarizer` 인터페이스 구현 (ML Kit에는 대응 기능 없음, LLM 어댑터로만 제공)
- [ ] PDF 화면에 "전체 문서 요약" 진입점 추가 (전체 번역이 아닌 요약으로 제공)
- [ ] 컨텍스트 한계를 넘는 문서에 대한 청크 분할 + 계층적 요약 로직 검토 (MVP는 컨텍스트 내 문서까지만 지원)

### 4-3. 설정/전환 UI (선택)
- [ ] 설정 화면에서 OCR/번역 엔진 선택 옵션 제공 여부 결정
- [ ] Qualifier 기반 다중 구현체 DI 전환 로직 (선택 시)

### 4-4. 비교 평가
- [ ] 동일 평가셋 기준 ML Kit vs Gemma 정확도/속도/메모리 비교
- [ ] 비교 리포트 문서화 (`docs/` 하위 신규 파일)

### 완료 조건 (DoD)
- Gemma 어댑터가 동일 인터페이스로 정상 동작하며 UI/도메인 코드 변경이 없다
- 어댑터별 비교 리포트가 작성되어 있다
- 저사양 기기(또는 낮은 RAM 조건)에서의 동작 여부가 확인되어 있다

## Phase 5 — 테스트/최적화/모니터링 강화

### 목표
품질과 안정성을 다지는 단계.

### 5-1. 테스트 커버리지
- [ ] domain UseCase/Reducer unit test 작성 (테스트 전략 문서 기준)
- [ ] ViewModel State/Intent/Effect 흐름 테스트
- [ ] 주요 시나리오 Compose UI Test

### 5-2. 모니터링
- [ ] Firebase Crashlytics 연동
- [ ] 모델 추론 성능 로그 태깅 (`ModelPerf` 등, AGENT.md 로깅 규칙 준수)

### 5-3. 벤치마크
- [ ] Macrobenchmark로 Cold Start/추론 지연시간 측정
- [ ] Android Profiler로 메모리 피크/배터리 소모 확인
- [ ] APK 용량 비교 (모델 번들 여부별)

### 5-4. 접근성/폼팩터
- [ ] TalkBack 확인, 폰트 스케일 대응 확인
- [ ] WindowSizeClass 기반 태블릿/폴더블 레이아웃 확인

### 완료 조건 (DoD)
- domain 모듈 커버리지 목표치 충족 (예: 80% 이상)
- 크래시 프리 세션 비율이 모니터링 대시보드에서 확인 가능하다
- 벤치마크 리포트가 문서화되어 있다

## Phase 6 — 배포 준비

### 목표
릴리즈 가능한 상태로 마무리.

### 태스크
- [ ] 릴리즈 서명/난독화(R8) 설정, 릴리즈 빌드에서 DEBUG 로그 비활성화 확인
- [ ] 스토어 등록 자료(스크린샷, 설명) 준비
- [ ] 최종 QA 체크리스트 실행 (Phase 1~5의 DoD 재확인)
- [ ] 개인정보처리방침 등 프라이버시 관련 문서 준비 (온디바이스 처리 명시)

### 완료 조건 (DoD)
- 릴리즈 빌드가 정상 설치/실행되며 크래시가 없다
- 모든 Phase의 DoD가 재검증되어 있다

## Phase 간 공통 규칙

- 각 Phase 시작 전, 해당 Phase에서 참조할 기준 문서(PRD/아키텍처/인터페이스 명세)를 다시 확인한다
- Phase 진행 중 구조적 결정이 필요하면 ADR(선택 문서)로 기록하고, 필요 시 AGENT.md/아키텍처 문서를 갱신한다
- 다음 Phase로 넘어가기 전 위 DoD 체크리스트를 실제로 체크하고 커밋 로그에 남긴다
